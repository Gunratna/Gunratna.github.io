How this website was built — explained from absolute zero

This guide assumes you have never written a line of code. It explains every idea behind your portfolio website — from "what even is a website" all the way to the realistic 3D room — one small step at a time, with plain language and everyday analogies.

How to read this: Go top to bottom. Each section builds on the last. When you meet a new word, it's explained the first time it appears, and again in the Glossary at the end. Nothing here is skippable-but-nothing here is hard. Take your time.

1 · What even is a website?

When you open gunratna.github.io, a few invisible things happen in under a second.

Analogy: Think of the internet as a giant city of libraries. Your browser (Chrome, Safari, Edge) is a courier. When you type an address, the courier runs to the right library (a server, which is just an always-on computer), asks for a specific book (your website's files), brings copies back, and lays them out on your screen.

  • Browser — the app on your phone/laptop that shows websites. It knows how to read website files and paint them into what you see.
  • Server — a computer somewhere that stays on 24/7 and hands out website files when asked. Your site's server is GitHub Pages (free, run by GitHub).
  • URL / address — the text like gunratna.github.io that tells the courier which library and which book.
  • Files — a website is really just a folder of files (text, images, code) that the browser downloads and displays.

So a website is not a magical living thing — it's a folder of files that a browser downloads and draws. Everything below is about what's inside those files and how we made them.

2 · Frontend, backend, and what yours is

Software people split websites into two halves:

  • Frontend — everything that happens in the browser, on the visitor's screen: layout, colours, text, buttons, animations, the 3D room. "Front" = the part facing the user.
  • Backend — programs running on a server: databases, logins, saving data. "Back" = behind the scenes.
Your portfolio is a frontend-only, "static" website. There's no database and no server program you own. Every page is pre-built into plain files ahead of time and simply served as-is. That's why it can be hosted free on GitHub Pages. The one exception is the contact form, which hands its message to a third-party service (more on that later) instead of your own backend.

3 · The three languages every website speaks

Almost every website in the world is built from three core languages. They each have one job.

Analogy — building a house: HTML is the bricks and rooms (the structure). CSS is the paint, furniture, and interior design (the looks). JavaScript is the electricity and moving parts — lights that switch on, doors that open (the behaviour).

HTML — the structure

HTML (HyperText Markup Language) describes what things are: "this is a heading", "this is a paragraph", "this is a button", "this is an image". It uses tags written in angle brackets.

<h1>Gunratna Borkar</h1>
<p>Senior AI Engineer</p>
<button>Get in touch</button>

Each tag is like a labelled box. <h1> means "top-level heading". The browser reads these labels to understand the page.

CSS — the looks

CSS (Cascading Style Sheets) describes how things look: colours, sizes, spacing, fonts, positioning. You point at an element and give it style rules.

h1 {
  color: orange;      /* text colour */
  font-size: 40px;    /* how big */
}

JavaScript — the behaviour

JavaScript (JS) is a real programming language. It makes pages do things: respond to clicks, load data, animate, run the 3D scene. If HTML is the noun and CSS is the adjective, JavaScript is the verb.

button.addEventListener("click", function () {
  alert("Thanks for reaching out!");
});

Your whole site — including the 3D room — is ultimately these three, plus tools that make writing them easier (coming up).

4 · How files turn into the page you see

When the browser downloads your files, it does three things in order:

  1. Parses the HTML into a tree of boxes called the DOM (Document Object Model) — think of it as the browser's live checklist of everything on the page.
  2. Applies the CSS to paint and position each box.
  3. Runs the JavaScript, which can then change any box at any time (add a menu, start the 3D canvas, etc.).
Analogy: The DOM is like a stage. HTML sets up the props, CSS designs the set, and JavaScript is the director who can move props around while the show is running.

5 · Programming basics (the mental model)

You don't need to code to understand your site, but a handful of ideas unlock everything else.

  • Variable — a labelled container that holds a value. name = "Gunratna". Later you can read or change what's inside.
  • Type — what kind of value it is: text (a "string"), a number, true/false (a "boolean"), a list, etc.
  • Function — a reusable recipe. You give it ingredients (inputs), it does steps, and returns a result. add(2, 3) returns 5.
  • Condition — a decision: "if the connection is slow, then use the lighter version."
  • Loop — "do this for each item": for each project, draw a card.
Analogy: A function is a coffee machine. Beans + water go in (inputs), a fixed process runs, coffee comes out (output). You don't rebuild the machine each morning — you reuse it. Good software is mostly small, well-named machines wired together.

6 · TypeScript — JavaScript with a safety net

Plain JavaScript lets you make silent mistakes — like putting a number where text was expected — and you only find out when the page breaks. TypeScript is JavaScript plus type labels. You declare "this value must be text" and a checker warns you before the site ever runs if something doesn't match.

function greet(name: string) {   // name MUST be text
  return "Hi " + name;
}
greet(42);  // ❌ TypeScript flags this: 42 is a number, not text
Your project is written in TypeScript (the .ts and .tsx files). It's the industry standard for serious web apps because it catches whole categories of bugs early. Before the site is published, a build step confirms every type lines up.

7 · Thinking in components (this is the big one)

Modern websites aren't written as one giant HTML file. They're assembled from components: small, self-contained, reusable pieces of UI.

Analogy — LEGO: A component is a LEGO brick. You build a "Button" brick once, then click it into place anywhere, dozens of times. Bigger bricks are made of smaller bricks: a "ProjectCard" is made of a title, an image, and a button. The whole page is one big model made of nested bricks.

In your site, every visible chunk is a component: Navbar, Hero, ProjectCard, Footer, and in the 3D world, Room, Lighting, Chair. Benefits:

  • Reuse — build once, use everywhere.
  • Isolation — fix the Button in one place, every button updates.
  • Readability — a page reads like a table of contents: "Navbar, Hero, About, Projects…".

The library that gives us components is called React.

8 · React — props, state, and reactivity

React is the most popular tool for building component-based interfaces. Three ideas matter:

Props — inputs to a component

Props are the settings you pass into a component, like ingredients into a recipe. The same ProjectCard component shows different projects depending on the props you give it.

<ProjectCard name="Email BOT" type="LLM" />
<ProjectCard name="SEBI Debarred" type="RAG" />

State — a component's memory

State is information a component remembers that can change over time — for example, "is the menu open?" or "which vibe is selected in the 3D room?". When state changes, React automatically redraws just the parts that depend on it. You never manually update the screen; you change the state and React reacts (hence the name).

Analogy: State is like a thermostat's target temperature. You set it to a new value, and the system automatically responds — you don't manually push the warm air around. In the 3D room, clicking "Dev Cave" sets a state value to "cave", and React re-renders the scene with the moody lighting.

Hooks — plugging into React's powers

Hooks are special functions (their names start with use) that let a component use React features. You'll see them all over the code:

  • useState — give a component a piece of memory.
  • useEffect — run some setup when the component appears (e.g., start listening for keyboard shortcuts) and clean up when it leaves.
  • Custom hooks like useSceneQuality or useFocusTrap — your own reusable bundles of logic.

JSX is the friendly syntax that lets us write HTML-looking tags directly inside JavaScript. Files ending in .tsx are "TypeScript + JSX" — components written in TypeScript.

9 · Next.js — the framework that packages it all

React alone gives you components, but a real website needs more: multiple pages, fast loading, good search-engine visibility, a build process. Next.js is a framework built on top of React that provides all of that out of the box.

Analogy: React is an engine. Next.js is the whole car built around that engine — wheels, steering, dashboard — so you can actually drive somewhere instead of just admiring the motor.

What Next.js gives your site:

  • Routing — the folder structure becomes your pages. A folder app/lab/ automatically becomes the /lab page. Your home page is app/page.tsx.
  • A build step — it bundles, checks, and optimises everything into a tidy set of files for the browser.
  • Static export — the mode your site uses (next section).
  • Image, font, and SEO helpers — for speed and discoverability.

10 · When does the page get built? (static export)

There are a few strategies for when a page's HTML is created:

StrategyWhen HTML is madeNeeds a live server?
Client-rendered (CSR)In the browser, after JS loadsNo, but slow first paint
Server-rendered (SSR)On each request, by a serverYes
Static (SSG / export)Once, ahead of time, during the buildNo

Your site uses static export (output: "export" in the config). Every page is turned into a finished HTML file at build time and dropped into a folder called out/. Those files are then just handed to visitors.

Why this matters for you: static files can live on free hosting (GitHub Pages), load extremely fast, and have nothing to hack or crash. The trade-off — no live server logic — is fine here, because a portfolio doesn't need one. The 3D room still runs live in the browser; only the page's HTML shell is pre-built.

11 · Styling: design tokens, Tailwind, and theming

Design tokens

Instead of scattering colours like #e08a33 everywhere, the site defines them once as named CSS variables (design tokens): --accent, --bg, --text. Everything refers to the token. Change the token once and the whole site updates.

Theming (dark / light)

The site supports dark and light themes by swapping those token values based on a data-theme label on the page. A tiny script even remembers your choice between visits.

Tailwind CSS

Tailwind is a styling system where you compose designs from many tiny, single-purpose classes right in the markup, instead of writing separate CSS files.

<button class="rounded-lg bg-accent px-5 py-3 text-white">
  Send message
</button>
Analogy: Tailwind is like having a labelled drawer for every small adjustment — "rounded corners", "medium padding", "accent background". You grab the drawers you need instead of tailoring a bespoke outfit every time. Faster, and everything stays visually consistent.

12 · A tour of your portfolio, section by section

The home page stacks these components top to bottom, each one its own file:

  • Navbar — the top navigation bar.
  • Hero — the big opening: your name, tagline (typed out letter by letter), buttons, and a subtle floating particle field.
  • About — bio, animated counters (numbers that count up), and a fake terminal.
  • Experience — a vertical timeline of roles; the current role has a gently pulsing dot.
  • Projects — filterable cards; clicking one opens a modal (a pop-up window) with an architecture diagram.
  • Skills, Education, Contact, Footer.

Sprinkled on top are extras: a Command Palette (press Ctrl/Cmd + K to jump anywhere), a custom cursor, and toasts. All of these are components, all reusing the same design tokens.

One important content idea: a single source of truth. All your real information (jobs, projects, skills) lives in one file, content.ts. Every section — and the 3D room's project stations — reads from that one file, so you update your info in exactly one place.

13 · The contact form: input, validation, delivery

The contact form shows three classic frontend jobs:

  • Capturing input — reading what the visitor types.
  • Validation — checking it before sending. A tool called Zod defines the rules ("email must look like an email", "message at least 10 characters"), and React Hook Form manages the fields and error messages.
  • Delivery — since there's no backend, the form hands the message to Formspree, a third-party service that emails it to you. If that ever fails, it falls back to opening your email app so the message is never lost.
There's also a hidden honeypot field — a decoy input invisible to humans but tempting to spam bots. If it gets filled, we know it's a bot and ignore it.

14 · Being found: SEO and metadata

SEO (Search Engine Optimisation) is making your site understandable to Google and to social apps. It's mostly invisible information attached to the page:

  • Metadata — the title, description, and keywords search engines read. Your layout defines these carefully ("Gunratna Borkar — AI Engineer | IIT Bombay").
  • Open Graph tags — control the preview card shown when your link is shared on LinkedIn/WhatsApp/etc. There's even an auto-generated preview image.
  • JSON-LD (structured data) — a machine-readable summary that tells Google "this is a Person named Gunratna, job title Senior AI Engineer, studied at IIT Bombay". This can produce richer search results.
  • sitemap.xml & robots.txt — a map of your pages for search crawlers, and rules about what they may visit.
Analogy: SEO metadata is the label on a tin. The soup inside is the same, but a clear, honest label helps the right people find it on the shelf and know what's inside before opening.

15 · Accessibility — building for everyone

Accessibility (often shortened to "a11y") means people with disabilities can use the site too — those using screen readers, keyboards instead of mice, or who need reduced motion. It's both the right thing to do and often a legal expectation. Examples in your site:

  • Labelled form fields so screen readers announce "Email, edit text" correctly.
  • Focus trapping in pop-ups: when a dialog opens, keyboard focus stays inside it and returns to where you were on close, so keyboard users don't get lost.
  • Reduced motion: if a visitor's device asks for less animation (a system setting for people who get motion sickness), the looping animations and the auto-spinning 3D camera switch off.
  • A non-3D fallback: the /lab page also lists every project as plain text, so the content is reachable even without 3D or a mouse.

16 · Performance — staying fast on every device

Rich sites can get heavy. Three techniques keep yours quick:

  • Code splitting & lazy loading — the heavy 3D code isn't downloaded when someone visits the home page. It's only fetched if and when they open the /lab room. The browser doesn't pay for what it doesn't use.
  • Quality tiers (Full vs Lite) — the site detects slow connections or weak devices and automatically dials things down (fewer effects, lower resolution). The 3D room reads this too: on "Lite" it skips the expensive post-processing.
  • Pausing work — when you switch browser tabs, the 3D room stops rendering entirely to save battery, and resumes when you return.
Analogy: It's like a car that idles the engine at a red light and only kicks into sport mode when the road (your device) can handle it.
The 3D world

17 · The 3D room, part A: how 3D graphics work at all

Now the fun part. How does a flat screen show a room you can orbit around?

The GPU

Your device has two brains: the CPU (general thinking) and the GPU (Graphics Processing Unit — a specialist that does the massive maths of drawing millions of coloured dots very fast). All 3D leans on the GPU.

WebGL

WebGL is the browser's doorway to the GPU. It lets a website ask the GPU to draw 3D. It's powerful but extremely low-level — like machine code for graphics. Writing it directly is painful.

Three.js

Three.js is a friendly library that sits on top of WebGL. Instead of raw GPU instructions, you say "make a box", "add a light", "point a camera here". It's the de-facto standard for 3D on the web.

React Three Fiber (R3F)

React Three Fiber lets you build a Three.js scene using React components — the same LEGO-brick idea as the rest of your site. So a chair becomes a <Chair /> component, a light becomes <directionalLight />. This is why the 3D world feels consistent with the rest of the codebase.

Analogy — the stack: The GPU is the printing press. WebGL is the raw, fiddly control panel. Three.js is a comfortable operator's console with labelled buttons. React Three Fiber is a well-organised checklist for that console. Each layer makes the one below easier to use.

The scene graph

A 3D scene is a tree of objects (the "scene graph"), just like the DOM was a tree of HTML boxes. The room contains a desk; the desk contains a top and legs; each has a position. Move the desk and everything on it moves too, because children follow their parent.

18 · The 3D room, part B: meshes, geometry, and realistic materials

Mesh = geometry + material

Every solid object is a mesh, and a mesh is two things combined:

  • Geometry — the shape: the invisible wireframe of points and triangles. (All 3D shapes are ultimately made of triangles.) A box, a cylinder, a plane.
  • Material — the surface: how it looks and responds to light — its colour, shininess, bumpiness.

PBR — physically based rendering

The key to realism is PBR: describing surfaces by real physical properties so they respond to light like real materials do. The main dials:

  • Base colour — the raw colour of the surface.
  • Roughness — smooth (mirror-like, sharp reflections) vs rough (matte, blurry reflections). Polished metal is low roughness; a wool rug is high.
  • Metalness — is it metal or not? Metals reflect differently from wood or fabric.
  • Normal — a trick that fakes tiny bumps and grain without adding real geometry, so wood looks textured and grooved while staying a flat, cheap surface.

Textures

A texture is an image wrapped onto a surface. Real PBR materials use several images at once for one surface:

  • Colour map — the visible pattern (wood grain photo).
  • Normal map — a special purple-ish image encoding the bumps.
  • Roughness / metalness / AO maps — greyscale images saying how rough/metallic/shadowed each spot is.
This is the single biggest reason your room started looking real. The first version used flat solid colours — obviously fake. Now the floor, walls, desk, leather chair, and rug use real photographed material images (with all these maps) sourced from Poly Haven. Light hits them unevenly, exactly like real surfaces.

19 · The 3D room, part C: light, shadow, and atmosphere

Materials only look real if the light is real. Lighting, more than anything, separates "a 3D model" from "a photograph". The room uses several light sources working together.

The lights

  • Directional light (the "sun") — parallel rays from one direction, like real sunlight. It's the main light and the one that casts shadows.
  • Hemisphere light — a soft two-colour fill: sky colour from above, ground colour bouncing from below. It mimics how the real sky gently lights everything, so shadows aren't pitch black.
  • Point lights — glow from a single spot, like the desk lamp bulb or the monitors, spreading in all directions and fading with distance.

Shadows

Shadows are computed by rendering the scene once from the light's point of view to see what's blocked. This is stored in a shadow map. A higher-resolution shadow map (yours is 2048×2048) gives crisper shadows. Small tweaks ("bias") stop objects from casting ugly shadows on themselves. We use soft shadows so edges are gently blurred, like real life, not hard cutouts.

HDRI & image-based lighting

An HDRI is a 360° photograph of a real place that stores real light intensities (much brighter range than a normal photo). We wrap the scene in one. Now every shiny surface reflects a believable real environment, and the overall light has the warmth and subtlety of a real room. This technique is called image-based lighting (IBL).

Analogy: Instead of guessing where to place lamps, IBL is like carrying your object into an actual photographed room — it's automatically lit by everything around it, reflections and all.

Environment maps & PMREM

To make reflections cheap enough for real time, the HDRI is pre-processed into an environment map (via a tool called PMREM). It's blurred at several levels so rough surfaces get soft reflections and smooth surfaces get sharp ones — automatically.

Tone mapping

Real light has a far wider brightness range than a screen can show. Tone mapping squeezes that range into what the screen can display, in a cinematic way. We use ACES Filmic tone mapping — the same family of curves used in film — which is why the room looks "shot" rather than "computed".

Fog

A subtle fog tinted to match the horizon fades distant objects slightly, adding depth and mood — much like real air over distance.

20 · The 3D room, part D: cinematic post-processing, camera, and the loop

Post-processing

Post-processing means effects applied to the finished image after the 3D is drawn, like filters on a photo. The room's pipeline adds, in order:

  • SSAO (Screen-Space Ambient Occlusion) — darkens crevices and contact points (where the chair legs meet the floor, corners of the room). Real light struggles to reach tight nooks; SSAO fakes that subtle shading and instantly grounds objects.
  • Bloom — makes bright things (the monitors, the lamp) softly glow and bleed light, like a camera catching a bright source. This is what makes the "Dev Cave" screens feel like they're really glowing in the dark.
  • Vignette — gently darkens the corners of the frame to focus your eye, a classic cinematic touch.
  • SMAA — smooths jagged, stair-stepped edges (anti-aliasing) so lines look clean.

The two vibes

The Cozy Study and Dev Cave switches are really just bundles of the settings above: light colours and intensity, HDRI strength, fog, window brightness (day vs night), monitor glow, and bloom/vignette amounts. Flip the switch and React re-applies a whole different mood using the exact same room.

Camera & controls

A virtual camera is your eye in the scene. OrbitControls let you drag to rotate around a target and scroll to zoom, with damping (a little momentum) so it feels weighty and natural rather than snappy. Limits stop you from flying through walls.

The render loop

Animation is an illusion of many still frames shown quickly (ideally 60 per second). The render loop draws a fresh frame over and over. To keep motion smooth regardless of device speed, movement is scaled by the real time elapsed between frames — so things move at the same real-world speed on a fast or slow machine.

21 · Where the realistic assets come from (and the licence)

The realistic textures and the HDRI come from Poly Haven, a library of high-quality 3D assets released under the CC0 licence.

CC0 means "no rights reserved" — public domain. You can use the assets for anything, including commercial projects, with no attribution required. That's why they're safe to download, commit into your project, and ship on a public, free site. We deliberately used the small "1k" versions (~700 KB each) so the room loads quickly.

22 · From your laptop to the live web: Git, GitHub, and automatic deployment

Git — a time machine for code

Git records snapshots ("commits") of your project over time. You can see history, undo mistakes, and work in parallel "branches". Think of it as an infinite, organised undo history with labels.

GitHub — the shared home for the code

GitHub is a website that stores Git projects online, so your code is backed up and shareable. Your project lives in a GitHub repository ("repo").

GitHub Actions — the robot assistant (CI/CD)

Every time you save new code to GitHub, a robot recipe (a GitHub Action) automatically wakes up and:

  1. Installs the project's tools.
  2. Runs the Next.js build (checks types, bundles everything, exports the static files to out/).
  3. Publishes those files to GitHub Pages.

This automation is called CI/CD (Continuous Integration / Continuous Deployment). You just save your work; the site updates itself minutes later — for free.

Analogy: You drop off a manuscript (your code). The robot printer proofreads it, prints the final books (the build), and stocks the library shelves (GitHub Pages) — automatically, every single time, without you lifting a finger.

23 · How it all fits together

Zooming all the way out, here's the whole journey of your project:

  1. You write components in TypeScript + JSX, using React for structure and Tailwind for looks.
  2. All your real content lives in one content file, feeding both the page sections and the 3D room.
  3. The /lab room is a Three.js scene built with React Three Fiber, made realistic with PBR materials, HDRI lighting, shadows, tone mapping, and post-processing, with two switchable vibes.
  4. Next.js bundles it and statically exports plain files.
  5. GitHub Actions builds and deploys those files to GitHub Pages, live and free.
  6. A visitor's browser downloads the files, paints the page, and — if they open the lab — asks the GPU via WebGL to render the room in real time.

Every buzzword in this guide is just one small, sensible layer on top of the one below it. That's all software really is: friendly layers, stacked.
